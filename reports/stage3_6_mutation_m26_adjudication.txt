Current pipeline schedule
-------------------------
`kill` is `halted || fault`; `fault` comes from the valid EX/MEM instruction in MEM.
The iterative M start request is accepted only when `md_ready` and `!kill` are both true.

1. Same-cycle older fault and younger DIV start candidate: older instruction is in EX/MEM/MEM, DIV is in ID/EX/EX. The MEM fault makes `kill=1` combinationally in this same cycle. The `!kill` term suppresses `md_start_req`; at the edge the faulting instruction is not committed, the pipeline is killed, and the divider remains IDLE. Thus acceptance suppression handles this case; abort is not cancelling accepted work.
2. Older instruction is nonfaulting in MEM: it advances to MEM/WB at the edge. With the current combinational, no-wait-state memory interface, it cannot later raise a MEM fault. DIV may then be accepted. During its accepted/RUN interval, ID/EX holds DIV, EX/MEM receives bubbles, and younger instructions remain in IF/ID; no younger fault can reach MEM before DIV FIN transfers. The older instruction drains through WB. Therefore `kill` cannot newly assert during an already accepted unfinished DIV.
3. Redirects do not create this overlap: an older redirect resolves in EX before a younger DIV reaches ID/EX, so the younger DIV is flushed before acceptance. Reset resets the divider independently of its abort input.

Scope and classification
------------------------
Under the current in-order pipeline, faults resolved in MEM, no interrupts/traps that asynchronously kill execution, no external kill, and no memory wait states, the changed abort connection is unobservable for every reachable pipeline execution.
